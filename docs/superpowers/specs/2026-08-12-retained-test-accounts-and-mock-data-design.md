# 保留测试账号与全流程模拟数据设计

## 1. 目标

在不覆盖线上历史业务数据的前提下，统一测试账号、人员档案和全流程模拟数据：仅保留指定 7 个账号为有效状态，其他账号停用但保留历史记录；为指定人员补齐可重复执行、可追踪、可计算绩效的工单和排班数据。

| `13800000002` | 张师傅 | `worker` | 维修师傅 | `active` |
| `13800000003` | 李师傅 | `worker` | 维修师傅 | `active` |
| `13800000004` | 王师傅 | `worker` | 维修师傅 | `active` |

测试密码统一使用用户确认的值，但具体明文不进入版本库。执行迁移时通过 `RETAINED_TEST_PASSWORD` 环境变量传入并使用 bcrypt 哈希保存；脚本、日志、数据库导出摘要和 Git 历史不得记录明文密码。

主管账号是唯一最高权限账号。其他 6 个账号不能通过客户端参数提升为主管。

## 3. 其他账号的处理规则

不在固定手机号清单中的账号全部执行逻辑停用：

- `users.status` 更新为 `disabled`；
- 对应 `staff_profiles.employment_status` 更新为 `inactive`；
- 撤销其当前登录能力，既有 JWT 因服务端回查账号状态而立即失效；
- 清理当前小区成员关系、未来排班、考勤和实时在岗状态；
- 保留历史工单、工单活动日志、报告缓存和 AI 分析记录；
- 停用人员默认不出现在人员选择框、通讯录、组织树和当前绩效汇总中；
- 历史报表仍能通过原负责人名称或用户标识解释其历史贡献，不把历史工单改挂到其他人员。

脚本不得物理删除账号、档案、工单或历史日志。

## 4. 数据迁移与备份顺序

线上数据是迁移基准，禁止使用本地 `data.db` 直接覆盖线上数据库。执行顺序固定为：

1. 下载 Supabase `production/data.db` 远程快照；
2. 复制 Render `/var/data/data.db` 作为执行前备份；
3. 记录两份数据库的 SHA-256、表集合和各表记录数；
4. 若远程与 Render 当前数据库不一致，以 Render 当前运行数据库为候选主库，并暂停写入后再次制作快照；
5. 在候选副本上执行迁移和模拟数据脚本；
6. 完成结构、记录数、账号和业务链路验证；
7. 原子替换 Render 运行数据库并上传 Supabase 新快照；
8. 再次比较哈希、表集合和各表记录数；
9. 验证通过后恢复服务流量。

任何一步失败均停止后续替换，并保留原数据库和备份文件。

## 5. 人员档案与组织关系

脚本按手机号关联 `users` 和 `staff_profiles`，保证一个账号最多对应一个人员档案：

- 主管为组织根节点；
- 4 名维修师傅和 2 名物业管家的直属上级均为主管；
- 姓名、手机号、角色、职位、在职状态保持与固定清单一致；
- 原有出生年月、入职日期、技能等非空资料优先保留，脚本只补缺失值；
- 7 人加入默认测试小区；如线上存在多个小区，则额外建立一个模拟小区用于跨小区权限验证，但不得改变真实小区名称或授权。

## 6. 模拟数据命名和幂等规则

所有新增模拟业务数据使用稳定前缀：

- 工单：`MOCK-E2E-`；
- 小区：`mock-e2e-community`；
- 班次模板：`模拟白班`、`模拟夜班`；
- 导入批次、活动标识和备注均包含 `MOCK-E2E`。

幂等键使用固定业务 ID、手机号、日期和模板名称。重复执行时：

- 已存在的模拟记录按安全白名单字段更新；
- 不重复插入同一工单、排班或活动；
- 不修改、不合并、不删除任何非 `MOCK-E2E` 历史工单；
- 不改变真实工单的负责人、状态、完成时间或绩效规则版本。

模拟日期以执行日为基准动态生成，使首页、本月报告和近日历始终有可见数据；固定业务 ID 保证重复执行仍可定位同一记录。

## 7. 工单场景覆盖

模拟数据至少覆盖以下场景：

| 场景 | 目的 |
| --- | --- |
| 待派单 | 验证主管派单、首页待处理和提醒 |
| 处理中 | 验证师傅当前任务、日程和主管看板 |
| 搁置中 | 验证搁置原因和恢复流程 |
| 待确认 | 验证管家确认和退回 |
| 已完成 | 验证完成量、处理时长、SLA 和绩效 |
| 退回记录 | 验证质量扣分和活动时间线 |
| 复发工单 | 验证复发识别及质量评分 |
| 多人反馈 | 验证重复反馈计数和报告风险提示 |
| 紧急工单 | 验证优先级、SLA 和主管首页 |
| 多小区工单 | 验证 `community_id`、跨小区隔离和报告筛选 |

每名维修师傅至少拥有 5 张已完成模拟工单及 1 张当前工单；每名管家至少拥有确认、退回或协作处理记录；主管至少拥有派单、审核和状态操作日志。样本需足够触发服务端绩效计算，不用前端伪造分数。

## 8. 排班、请假和冲突覆盖

模拟排班包含：

- 正常白班；
- 跨夜班；
- 事假或病假；
- 同一人员的工单与请假冲突；
- 同一人员的两个工单时间冲突；
- 未安排班次的空状态。

日历以服务端班次、请假和工单时间为事实来源，不恢复已删除的考勤展示模块。模拟考勤记录仅在后端兼容测试需要时生成，不在首页、个人中心或报告中展示。

## 9. 绩效与报告数据

每名测试人员的模拟工单必须携带可计算的负责人、派单时间、完成时间、预计时长、反馈次数、复发标记和绩效规则版本。

预期结果：

- 4 名维修师傅均能生成非空个人报告；
- 2 名管家能看到自己的协作/确认结果及有样本时的绩效；
- 主管能生成任意人员、日期、小区筛选报告；
- “全部人员”报告包含 7 人且排除 inactive 人员；
- AI 润色输入只包含脱敏聚合数据；AI 未配置或超时时，原始报告仍完整显示。

## 10. 执行接口与安全开关

迁移脚本必须同时满足以下条件才允许修改数据库：

- 显式指定目标数据库绝对路径；
- 显式设置确认参数；
- 显式传入测试密码环境变量；
- 目标数据库已创建同目录备份；
- 默认拒绝使用项目根目录的本地开发 `data.db` 作为线上覆盖源。

提供 dry-run 模式，只输出：保留账号数量、将停用账号数量、将新增/更新的模拟记录数量、表级记录数差异，不输出密码哈希、令牌、密钥或完整个人敏感信息。

## 11. 验证标准

迁移完成必须满足：

1. 7 个固定账号均可使用测试密码登录且角色正确；
2. 其他账号无法登录，旧 JWT 返回 401；
3. 人员列表、通讯录和组织树只显示 7 个 active 人员；
4. 每名人员均有完整档案和正确直属上级；
5. 模拟工单覆盖全部指定状态，活动时间线可解释；
6. 普通人员不能跨小区查看工单、通讯录或附件；
7. 单人报告、全部人员报告和绩效均有有效样本；
8. 脚本连续执行两次后记录数保持稳定；
9. Render 重启后账号、工单、排班和报告数据保持一致；
10. Supabase 快照与 Render 数据库的表集合和各表记录数一致；
11. 全量自动化测试通过；
12. 可使用执行前备份完成一次只读恢复验证。

## 12. 不在本次范围内

- 不接入短信验证码或双因素认证；
- 不把测试账号改造成正式员工账号；
- 不删除真实历史工单或审计日志；
- 不自动清空现有真实小区；
- 不在 GitHub、前端代码、Render 配置文件或文档中保存测试密码明文。
