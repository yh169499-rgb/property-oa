# 人员组织、排班考勤、主管工作台与人员报告设计

> 日期：2026-07-30  
> 状态：已完成交互确认，等待书面规格复核  
> 适用项目：智慧物业 OA 工单协同管理系统

## 1. 背景

当前系统已经具备工单管理、人员状态、日程、看板和报告能力，但相关数据存在以下限制：

- 人员技能、值班时间和入职日期主要保存在浏览器 `localStorage`，无法跨设备保持一致。
- 主管没有独立、完整的“我的”页面。
- 人员之间没有可维护的直属上下级关系。
- 当前排班日历视觉层次较弱，桌面和窄屏没有分别优化。
- 工单报告只能按小区和时间查询，不能选择具体人员。
- “本月工单总量”实际使用当前加载的全部工单。
- “本月出勤”由日期估算，不是实际打卡和排班数据。
- 主管的派单、催办、驳回和确认动作没有结构化操作日志，无法准确统计个人管理工作量。

本设计在保留现有 Express、sql.js、原生 HTML/CSS/JavaScript 技术栈的前提下，增加统一人员主数据、组织层级、排班考勤、工单操作日志和准确统计。

## 2. 已确认的关键决策

### 2.1 实现路线

采用渐进式服务端增强：

- 保留现有 Express 与原生前端。
- 新增服务端人员、组织、班次、考勤和操作日志模型。
- 不在本轮重写为 React/Vue。
- 不在本轮展开全部旧接口的安全整改。
- 新增能力必须使用 JWT 识别当前用户。

### 2.2 组织关系

采用单线上级树：

- 每人最多一位直接上级。
- 支持主管、组长、师傅等任意深度。
- 通过选择直属上级调整层级。
- 禁止循环管理关系。
- 不实现一人同时归属多个直属主管的矩阵组织。

### 2.3 考勤来源

采用每日排班驱动的实际考勤：

- 每日可安排工作班次、休息或请假。
- 员工通过系统签到、签退。
- 主管可以补卡和修正状态。
- 迟到和早退依据当天班次计算。
- 第一版不接入定位、人脸识别和第三方考勤机。

### 2.4 主管统计

同时展示两类数据：

- 个人管理动作：派单、催办、驳回、确认等。
- 团队处理成果：所辖人员的接单、完成、超时和按时率。

### 2.5 人员报告时间口径

同一份报告同时展示：

- 期间接单量：按派单时间；历史缺少派单日志时使用工单创建时间回退。
- 期间完成量、处理时长和 SLA：按工单完成时间。

### 2.6 日历视觉方向

采用响应式组合：

- 桌面端默认使用飞书/Google 风格日视图。
- 窄屏自动切换为人员议程卡片。
- 两种视图共享相同数据和业务规则。

### 2.7 导航结构

主管导航：

```text
首页｜报修｜投诉｜帮助｜已完成｜管理工作台｜我的
```

“组织”“排班”和原“管理平台”合并到“管理工作台”。

普通人员不显示“管理工作台”，个人排班、打卡和考勤进入“我的”。

## 3. 范围

### 3.1 本轮包含

- 服务端统一人员档案。
- 可配置直属上级和组织树。
- 主管独立“我的”页面。
- 主管指挥中心首页。
- 管理工作台。
- 每日排班和班次模板。
- 签到、签退、请假、补卡和考勤异常。
- 桌面日视图与窄屏人员议程。
- 工单操作日志。
- 主管个人动作和团队成果统计。
- 按人员和时间生成报告。
- 本月工单统计口径修正。
- 旧用户、旧负责人姓名和 localStorage 人员资料的兼容迁移。

### 3.2 本轮不包含

- 全量旧 API 权限整改。
- 多主管矩阵组织。
- GPS、Wi-Fi、人脸或设备绑定打卡。
- 薪资、加班费和工时结算。
- 复杂审批流。
- 一天多段拆分班次。
- 第三方考勤机同步。
- 前端框架重写。
- 数据库产品迁移。

## 4. 页面信息架构

### 4.1 首页

首页替代含义模糊的“概览”，采用指挥中心布局。

展示：

- 今日待办。
- 待派单工单。
- SLA 超时工单。
- 今日主管管理动作。
- 团队到岗人数。
- 本月团队完成量。
- 直属人员当前状态。
- 需要处理的考勤异常。

首页面向“今天需要处理什么”，不承担完整人员资料或完整报表功能。

### 4.2 我的

主管和普通人员均有独立“我的”页面，内容按角色变化。

#### 基本资料

- 姓名。
- 出生年月。
- 入职日期。
- 手机号。
- 职位。
- 直属上级。
- 工龄。

本人可编辑：

- 手机号。
- 出生年月。

仅管理工作台可编辑：

- 入职日期。
- 职位。
- 直属上级。
- 技能。
- 在职状态。

#### 主管个人统计

按今日、本月、本年切换：

- 派单数。
- 催办数。
- 驳回数。
- 确认完成数。
- 其他已纳入日志的管理动作。

#### 主管团队统计

按今日、本月、本年切换：

- 接单数。
- 完成数。
- 处理中数。
- 搁置数。
- 超时数。
- SLA 按时完成率。

团队范围为主管全部递归下级，而不只是直接下级。

#### 个人考勤

- 今日排班。
- 当前签到/签退状态。
- 签到和签退按钮。
- 本月实际出勤天数。
- 迟到、早退、请假、缺卡数量。
- 月历式逐日考勤明细。

### 4.3 管理工作台

使用标签页组织主管专属能力：

1. 人员组织
2. 排班日历
3. 考勤管理
4. 注册审核
5. 人员报告
6. 小区与系统设置

#### 人员组织

- 展开/收起组织树。
- 搜索并定位人员。
- 节点展示姓名、职位、在岗状态和直属人数。
- 点击节点进入人员详情。
- 通过“调整直属上级”修改层级。
- 保存前预览移动后的组织结构。
- 未指定上级的人员进入“未分配人员”。

第一版不使用拖拽修改层级，避免误操作。

#### 排班日历

- 日期选择。
- 人员选择。
- 直属团队筛选。
- 当前小区或全部授权小区筛选。
- 桌面日视图。
- 窄屏议程视图。
- 新增、编辑和批量安排班次。
- 显示休息和请假。
- 显示工单时间块。
- 显示冲突。

#### 考勤管理

- 按日期、人员和团队查询。
- 展示应到、实到、迟到、早退、请假和缺卡。
- 主管补卡。
- 修改考勤状态。
- 查看修改记录。

#### 人员报告

- 人员选择。
- 今日、本周、本月快捷范围。
- 自定义起止日期。
- 当前小区或全部授权小区。
- 报告预览、复制、打印和 Word 下载。

## 5. 数据模型

### 5.1 `staff_profiles`

人员业务档案，与登录账号分离。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 人员档案 ID |
| `user_id` | INTEGER UNIQUE | 关联 `users.id` |
| `name` | TEXT | 姓名 |
| `birth_month` | TEXT | `YYYY-MM` |
| `join_date` | TEXT | `YYYY-MM-DD` |
| `phone` | TEXT | 联系手机号 |
| `position` | TEXT | 职位名称 |
| `skill` | TEXT | 技能描述 |
| `manager_id` | INTEGER NULL | 直属上级档案 ID |
| `employment_status` | TEXT | `active`、`inactive` |
| `created_at` | TEXT | 创建时间 |
| `updated_at` | TEXT | 更新时间 |

约束：

- `manager_id` 不得等于自身 ID。
- 更新 `manager_id` 前执行循环检测。
- `user_id` 唯一。
- 手机号与登录账号手机号修改需要同步。

### 5.2 `shift_templates`

可复用班次模板。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 模板 ID |
| `name` | TEXT | 模板名 |
| `start_time` | TEXT | `HH:mm` |
| `end_time` | TEXT | `HH:mm` |
| `color` | TEXT | 日历颜色 |
| `grace_minutes` | INTEGER | 迟到/早退宽限，默认 5 |
| `created_by` | INTEGER | 创建人 |

`end_time` 早于或等于 `start_time` 时表示跨午夜。

### 5.3 `shift_assignments`

某人某日的实际安排。第一版每人每天最多一个有效安排。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 安排 ID |
| `staff_id` | INTEGER | 人员档案 ID |
| `work_date` | TEXT | 班次归属日期 |
| `assignment_type` | TEXT | `work`、`rest`、`leave` |
| `template_id` | INTEGER NULL | 班次模板 |
| `start_at` | TEXT NULL | 工作班次开始时间 |
| `end_at` | TEXT NULL | 工作班次结束时间 |
| `leave_type` | TEXT NULL | 请假类型 |
| `note` | TEXT | 备注 |
| `created_by` | INTEGER | 创建人 |
| `updated_at` | TEXT | 更新时间 |

唯一约束：

```text
UNIQUE(staff_id, work_date)
```

### 5.4 `attendance_records`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 考勤记录 ID |
| `staff_id` | INTEGER | 人员档案 ID |
| `shift_assignment_id` | INTEGER | 对应排班 |
| `work_date` | TEXT | 归属日期 |
| `check_in_at` | TEXT NULL | 签到时间 |
| `check_out_at` | TEXT NULL | 签退时间 |
| `status` | TEXT | 计算后的考勤状态 |
| `is_corrected` | INTEGER | 是否被修正 |
| `updated_at` | TEXT | 更新时间 |

状态：

```text
not_started
normal
late
early_leave
late_and_early
missing_check_in
missing_check_out
leave
rest
absent
```

### 5.5 `attendance_change_logs`

保留主管补卡和修正记录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 记录 ID |
| `attendance_id` | INTEGER | 考勤记录 |
| `operator_user_id` | INTEGER | 操作人 |
| `before_json` | TEXT | 修改前 |
| `after_json` | TEXT | 修改后 |
| `reason` | TEXT | 必填原因 |
| `created_at` | TEXT | 操作时间 |

### 5.6 `ticket_activity_logs`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK | 日志 ID |
| `ticket_id` | TEXT | 工单号 |
| `actor_user_id` | INTEGER | 操作账号 |
| `actor_staff_id` | INTEGER NULL | 人员档案 |
| `action` | TEXT | 动作代码 |
| `metadata` | TEXT | JSON 扩展信息 |
| `created_at` | TEXT | 操作时间 |

首批动作代码：

```text
assign
urge
reject
approve_complete
return
suspend
resume
submit_result
```

### 5.7 `tickets` 扩展

新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `assignee_user_id` | INTEGER NULL | 当前负责人用户 ID |
| `assigned_at` | TEXT NULL | 最近一次派单时间 |

继续保留 `worker` 姓名字段，兼容旧接口和历史数据。

## 6. 组织层级规则

### 6.1 循环检测

将人员 A 的直属上级设为 B 前：

1. A 不能等于 B。
2. 从 B 开始沿 `manager_id` 向上遍历。
3. 如果遍历中遇到 A，则拒绝。
4. 返回 HTTP `409` 和明确的层级路径。

### 6.2 团队范围

主管团队统计使用递归下级：

```text
主管
  → 直接下级
  → 下级的下级
  → 直到叶子人员
```

人员报告选择单人时不自动包含其下级；主管“团队成果”才递归包含下级。

### 6.3 人员停用

本轮人员移除采用停用而非物理删除：

- `employment_status` 改为 `inactive`。
- 组织树默认隐藏停用人员。
- 历史工单、考勤和操作日志保留。
- 登录禁用将在后续安全整改中统一完成；本轮界面明确提示“停用档案不等于禁用登录账号”。

## 7. 排班和考勤规则

### 7.1 班次归属

- 普通班次归属开始日期。
- 跨午夜班次仍归属开始日期。
- 例如 `2026-07-30 22:00` 至 `2026-07-31 06:00` 属于 `2026-07-30`。

### 7.2 签到

- 必须登录。
- 必须存在当天 `work` 排班。
- 无排班时普通员工不能签到。
- 主管可以先创建临时班次。
- 重复签到返回已有签到时间，不重复写入。
- 使用服务器时间，不信任浏览器提交时间。

### 7.3 签退

- 必须已经签到。
- 重复签退返回已有签退时间。
- 跨夜班次签退仍写入原工作日考勤。

### 7.4 状态计算

默认宽限 5 分钟，以班次模板为准。

- 签到晚于 `start_at + grace`：迟到。
- 签退早于 `end_at - grace`：早退。
- 两者同时满足：迟到且早退。
- 到统计结算时间仍无签到：缺勤。
- 有签到无签退：缺签退。
- 主管修正后重新计算。

### 7.5 本月实际出勤

统计 `Asia/Shanghai` 当前自然月。

出勤一天必须满足：

- 当天为 `work` 排班。
- 存在实际或经审批补录的签到。
- 状态为正常、迟到、早退或迟到且早退。

不计出勤：

- 休息。
- 请假。
- 缺勤。
- 无排班。

## 8. 响应式日历设计

### 8.1 桌面日视图

布局：

- 左侧固定时间刻度。
- 每名人员一列。
- 人员列头固定。
- 工单和班次随时间纵向定位。

视觉规则：

- 轻量小时网格。
- 当前时间使用红色细线和圆点。
- 非值班区域使用浅灰斜纹。
- 工单使用带左侧色条的圆角卡片。
- 工单卡显示编号、分类、位置和时间。
- 冲突工单使用红色强调并左右错开。
- Hover 展示完整详情。

### 8.2 窄屏人员议程

断点下自动切换，不要求用户手动选择。

每个人员一张卡：

- 姓名和当前状态。
- 今日班次。
- 已排工时和剩余时间。
- 按时间排序的工单卡片。
- 冲突单独标红。
- 无工单时展示可派时段。

### 8.3 共享数据

桌面和窄屏视图都消费统一日历数据：

```text
人员
班次
休息/请假
工单时间块
考勤状态
冲突结果
```

前端只更换渲染方式，不重复业务计算。

## 9. 首页统计

### 9.1 本月工单总量

口径：

- 时区：`Asia/Shanghai`。
- 范围：当前所选小区。
- 起点：本月 1 日 00:00:00。
- 终点：下月 1 日 00:00:00，不包含终点。
- 时间字段：`tickets.created`。

本月报修、投诉和帮助数量使用相同月度集合。

### 9.2 其他卡片

- 当前紧急待处理：所有未完成紧急工单，不限月份。
- 本月平均处理时长：本月完成工单。
- 本月按时完成率：本月完成工单。
- 今日主管动作：今日 `ticket_activity_logs`。
- 团队到岗：今日排班与考勤。

卡片名称必须明确体现统计口径，避免“全部”与“本月”混淆。

## 10. 人员报告

### 10.1 筛选条件

- `staff_id`：必选单人。
- `from`：开始日期。
- `to`：结束日期。
- `community_id`：当前小区或全部授权小区。

快捷日期：

- 今日。
- 近 7 天。
- 本月。

结束日期转换为次日 00:00 的排他边界，避免漏掉结束日数据。

### 10.2 工单指标

接单口径：

- 优先使用 `assigned_at` 或 `ticket_activity_logs.action = assign`。
- 历史工单没有派单时间时使用创建时间，并在报告中标记为兼容口径。

完成口径：

- 使用 `finished`。
- 统计完成量、平均处理时长和 SLA 按时率。

其他指标：

- 当前处理中。
- 当前搁置。
- 期间退回。
- 复发工单。
- 多人反馈工单。
- 类型和分类分布。

### 10.3 考勤指标

- 应出勤天数。
- 实际出勤天数。
- 正常。
- 迟到。
- 早退。
- 请假。
- 缺勤。
- 缺卡。

### 10.4 主管报告

主管“我的”中增加：

- 个人动作报告。
- 递归团队成果报告。

个人动作来自操作日志，不从工单最终状态反推。

### 10.5 输出

继续支持：

- 页面预览。
- 复制文本。
- 打印。
- Word 兼容下载。

报告接口同时返回结构化 `stats`，便于页面图表展示。

```text
GET /api/calendar/day?date=&staff_id=&manager_id=&community_id=
```

返回人员、班次、考勤、工单时间块和冲突的统一结构。

`manager_id` 表示以该主管为根节点，筛选其全部递归下级；它不是独立的团队实体。

### 11.6 统计和报告

```text
GET /api/dashboard/stats?community_id=
GET /api/reports/staff/:staff_id?from=&to=&community_id=
GET /api/reports/manager/:staff_id?from=&to=&community_id=
```

## 12. 错误处理

统一使用 JSON：

```json
{
  "error": "错误说明",
  "code": "MACHINE_READABLE_CODE",
  "details": {}
}
```

主要状态：

- `400`：参数错误、日期错误、缺少修改原因。
- `401`：未登录或 Token 失效。
- `403`：无权查看或修改目标人员。
- `404`：人员、班次、考勤或工单不存在。
- `409`：组织循环、重复排班、班次冲突或状态冲突。
- `500`：未处理的服务端错误。

冲突响应必须返回可展示的具体人员、日期、时间和冲突对象。

## 13. 兼容迁移

### 13.1 数据库迁移

启动时创建新表和新字段，不删除旧表字段。

### 13.2 用户档案

- 为每个现有 `users` 账号创建 `staff_profiles`。
- 姓名和手机号来自 `users`。
- 职位根据 `users.role` 生成初始值。
- 出生年月、入职日期和直属上级为空，等待主管补全。

### 13.3 历史工单负责人

- 按唯一姓名匹配 `worker` 与人员档案。
- 匹配成功后写入 `assignee_user_id`。
- 同名或无匹配时不自动关联。
- 未关联记录进入管理工作台“待关联人员”列表。

### 13.4 localStorage 导入

主管首次进入升级后的管理工作台时：

1. 检查浏览器中是否存在旧人员资料。
2. 展示可导入字段和服务端现有字段。
3. 按手机号优先、姓名次之进行匹配。
4. 主管逐项确认冲突。
5. 导入技能、班次时间和入职日期。
6. 导入完成后记录版本，避免重复提示。

导入后服务端为人员资料唯一事实来源。

## 16. 验收标准

满足以下条件视为本轮完成：

1. 人员资料以服务端为准，跨浏览器一致。
2. 主管可以配置任意深度的单线上下级关系，且不能形成循环。
3. 主管拥有独立“我的”页面，并能查看个人动作和团队成果。
4. 员工可以根据每日排班签到和签退。
5. 本月出勤来自实际考勤记录。
6. 主管可以处理请假、补卡和异常考勤，并保留修改记录。
7. 桌面日历使用日视图，窄屏自动切换人员议程。
8. 人员报告可以选择人员、小区和时间范围。
9. 接单和完成使用已确认的双时间口径。
10. “本月工单总量”只统计当前自然月。
11. 现有工单、登录、照片和通知功能无阻断性回归。
