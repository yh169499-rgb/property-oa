# 主管四人团队、离职留痕与维修师傅工单范围设计

## 1. 背景与目标

系统只有一个最高权限账号“主管”。主管负责人员注册审批、组织关系、排班与工单管理，但直属在职团队必须受到明确容量约束：同时最多四人，岗位结构为三名维修师傅和一名管家。

人员离职后需要真正撤销并删除登录账号，同时保留其历史责任记录。历史工单、流转日志和历史绩效不能因账号删除而消失，所有涉及该人员的历史页面必须显示“姓名（已离职）”。离职释放对应岗位名额，主管可以继续审批或新增替补人员。

维修师傅除报修工单外，还需要看到并处理主管分配给自己的投诉工单和帮助工单。数据隔离必须由服务端根据当前登录账号强制执行，不能依赖前端隐藏或人员姓名匹配。

## 2. 已确认业务规则

### 2.1 账号与团队

- 系统只保留一个在职最高权限主管账号。
- 主管直属在职人员总数最多四人。
- 四个岗位槽位固定为：三名维修师傅、一名管家。
- 容量计算只统计 `employment_status = active` 且直属该主管的人员档案。
- 注册申请在满员时仍可提交并保留在待审核列表，但主管不能批准超出总数或岗位槽位的申请。
- 主管直接新增账号、为档案设置主管、恢复人员在职状态、批量导入人员等所有可能增加在职直属人员的入口，都必须使用同一套容量校验。
- 超出总人数返回 `409 TEAM_CAPACITY_FULL`；对应岗位已满返回 `409 ROLE_CAPACITY_FULL`。
- 不能通过先创建无主管人员、再调整主管等方式绕过容量规则。

### 2.2 离职

- “离职”是业务动作，不等同于删除历史人员档案。
- 离职事务成功后，`users` 中对应登录账号被删除，旧 JWT 因无法再找到有效用户而立即失效。
- `staff_profiles` 作为稳定历史身份保留，解除 `user_id`，状态变为 `departed`，记录离职时间和操作主管。
- 离职档案手机号只保留脱敏值，不保留密码、令牌或其他登录凭据。
- 当前小区成员关系、未来及当前排班、人员实时状态被移除；历史排班可保留为历史记录，但不参与当前日历和冲突计算。
- 不能离职或删除当前唯一主管。
- 离职人员不出现在当前组织树、通讯录、可派单人员、当前团队绩效和当前排班中。
- 历史工单、工单附件、流转记录、历史报告和历史绩效继续保留。
- 历史查询统一显示 `原姓名（已离职）`，不得显示“未知人员”或复用后来新员工的姓名。
- 离职释放其原岗位槽位；之后可以批准或新增同岗位替补人员，新人拥有新的人员档案 ID，不继承离职人员数据。

## 3. 数据模型

### 3.1 稳定历史身份

`users` 只承担认证身份；`staff_profiles` 承担人员业务身份和历史归属。新增或规范以下字段：

```text
staff_profiles.user_id              可空；在职账号对应 users.id，离职后置空
staff_profiles.employment_status    active | departed
staff_profiles.departed_at          可空，离职时间
staff_profiles.departed_by_user_id  可空，执行离职的主管
staff_profiles.phone                在职为当前手机号，离职后保存脱敏值
staff_profiles.manager_id           保留离职时的主管档案 ID，当前组织查询排除 departed
```

工单增加稳定人员档案引用：

```text
tickets.assignee_staff_profile_id   指向 staff_profiles.id，可空
```

- 新派单同时写入 `assignee_user_id` 与 `assignee_staff_profile_id`。
- 既有工单优先通过 `assignee_user_id -> staff_profiles.user_id` 回填档案 ID；无法唯一匹配时保留原 `worker` 姓名并产生迁移告警，不进行猜测式绑定。
- 离职时只清空该人员工单的 `assignee_user_id`，保留 `assignee_staff_profile_id` 和 `worker` 历史姓名。
- 工单活动继续使用已有 `actor_staff_id` 作为稳定历史身份；离职时清空其 `actor_user_id`，保留 `actor_staff_id`。
- 列表与报告显示名优先取人员档案；离职档案追加“（已离职）”。旧数据没有档案引用时回退到工单 `worker` 快照。

### 3.2 容量计算

新增独立的团队容量服务，输入主管档案 ID、目标岗位和可选排除档案 ID，输出当前占用和是否允许变更：

```text
总容量：4
维修师傅容量：3
管家容量：1
统计范围：直属主管 + active
```

该服务是以下路径的唯一容量判定来源：

- 审批注册申请；
- 主管直接创建人员账号；
- 新建人员档案；
- 修改人员直属主管；
- 把 `departed` 改回 `active`；
- 批量导入导致的主管或在职状态变更。

容量检查和写入必须放在同一个数据库事务中，避免两个并发审批同时通过导致第五名人员进入团队。

## 4. 离职事务

离职接口继续使用人员/账号删除入口，但响应语义明确为“账号已删除、历史档案已转为离职”。事务顺序如下：

1. 校验操作者为唯一主管，目标不是主管本人。
2. 查询并锁定目标账号与人员档案；已离职请求按幂等结果返回。
3. 将历史工单的稳定档案 ID 补齐，并清空 `assignee_user_id`。
4. 将历史活动的 `actor_staff_id` 补齐，并清空 `actor_user_id`。
5. 将档案标记为 `departed`，记录离职时间和操作人，手机号脱敏，`user_id` 置空。
6. 删除当前小区成员关系、当前/未来排班和人员实时状态。
7. 删除 `users` 登录账号。
8. 提交事务并持久化数据库；任一步骤失败则全部回滚。

API 成功响应示例：

```json
{
  "success": true,
  "accountDeleted": true,
  "historyRetained": true,
  "employmentStatus": "departed",
  "message": "账号已删除，历史工单已保留并标记为已离职"
}
```

## 5. 注册审批与新增人员

- 注册只接受 `worker` 和 `keeper`，注册申请不占团队名额。
- 审批时确定唯一主管档案，并进行容量检查。
- 审批通过在同一事务中创建 `users`、创建或绑定新的 `staff_profiles`、设置 `manager_id`、创建小区成员关系并更新申请状态。
- 不允许把新账号绑定到已离职档案；即使姓名或手机号相同也创建新的档案 ID。
- 主管直接新增人员走与注册审批相同的服务，不再由路由分别拼接用户和档案数据。
- 满员时待审核申请保持 `pending`，方便有人离职后再次审批。
- 列表向主管展示“当前 4/4、维修 3/3、管家 1/1”以及每项申请占用的岗位类型。

## 6. 维修师傅三类工单权限

### 6.1 服务端读取范围

对非主管账号，工单集合、详情、附件列表和日历工单统一限定：

```sql
tickets.assignee_user_id = 当前登录用户 ID
```

- 维修师傅可读取自己名下的 `repair`、`complaint`、`help` 三类工单。
- 管家仍只读取自己名下的三类工单。
- 未分配工单、他人工单即使属于同一小区也不可读取。
- 禁止用 `worker = 当前姓名` 作为主要授权条件；姓名仅用于显示和旧数据迁移。
- 主管不受个人归属限制，但仍按其授权小区范围管理。
- 访问他人工单统一返回 `404`，避免通过错误差异探测工单是否存在。

### 6.2 服务端操作范围

- 只有主管可以分配或改派工单、修改优先级、确认完成、删除工单。
- 维修师傅可以对自己名下的三类工单执行：开始处理、填写处理说明、上传现场材料、搁置、退回、提交主管审核。
- 管家维持相同的“仅本人名下”操作约束。
- 非主管不能修改 `worker`、`assignee_user_id`、`assignee_staff_profile_id`、`community_id` 或直接把工单设为最终完成。
- 已离职账号不存在，不能继续读取或操作历史工单。
- 每次状态变更写入活动日志，记录操作者的用户 ID 和稳定人员档案 ID。

### 6.3 前端

- 维修师傅导航显示：报修、投诉、帮助、已完成、我的。
- 三个列表复用同一套个人范围接口，不再隐藏投诉和帮助入口。
- 页面不再通过姓名做权限过滤；本地过滤只用于类型、状态和排序展示。
- 投诉、帮助工单对维修师傅显示与报修一致的处理、退回、搁置、上传材料和提交审核按钮。
- 主管派单界面三种类型均可选择任一在职维修师傅；已离职人员不会出现在候选列表。
- 历史工单详情和报告使用服务端返回的 `assigneeDisplayName`，例如“赵师傅（已离职）”。

## 7. 模拟数据调整

固定数据迁移工具改为：

- 仅五个可登录账号：一名主管、三名维修师傅、一名管家。
- 赵师傅、周管家转为两个无登录账号的 `departed` 历史档案。
- 四名在职人员各有报修、投诉、帮助工单，包含待处理、处理中、待审核和完成状态。
- 三名维修师傅分别至少拥有一张投诉工单和一张帮助工单，用于验证个人列表和处理流程。
- 两名离职人员只保留已完成历史工单、活动记录和历史绩效，不保留当前/未来排班或未完成工单。
- 组织、通讯录和可派单列表恰好显示主管直属四名在职人员。
- 验证器必须确认：五个账号可登录、两名离职人员不能登录、团队占用为 `4/4`、角色占用为 `3/3 + 1/1`、历史工单仍显示离职人员。

## 8. 错误处理和审计

| HTTP | 错误码 | 场景 |
|---|---|---|
| 409 | `TEAM_CAPACITY_FULL` | 主管已有四名直属在职人员 |
| 409 | `ROLE_CAPACITY_FULL` | 三名维修师傅或一名管家槽位已满 |
| 409 | `LAST_SUPERVISOR_REQUIRED` | 试图离职/删除唯一主管 |
| 409 | `PROFILE_ALREADY_DEPARTED` | 重复执行离职动作；接口也可按幂等成功返回 |
| 403 | `TICKET_SCOPE_FORBIDDEN` | 非主管试图修改他人工单；读取接口对外返回 404 |
| 400 | `INVALID_TICKET_TRANSITION` | 非法状态跳转或普通员工修改主管字段 |

离职、审批、拒绝、分配、改派和人员恢复均写入审计记录。审计记录保留主管用户 ID、目标人员档案 ID、动作时间、动作类型和非敏感摘要，不记录密码、JWT 或完整密钥。

## 9. 迁移、回滚与上线

- 先部署兼容新旧字段的代码，再迁移数据库，避免迁移窗口内旧代码无法读取。
- 生产迁移前同时备份 Render 持久化数据库和 Supabase 远程对象。
- dry-run 输出账号变化、在职/离职档案变化、工单回填数量、无法唯一匹配数量和团队容量结果。
- 任何无法唯一匹配的历史人员都只生成告警，不自动绑定到同名人员。
- 数据迁移验证通过后才替换生产数据库并同步 Supabase。
- 回滚以迁移前数据库快照为准；若代码已经部署，可继续读取旧结构。

## 10. 验收标准

### 10.1 团队容量

- 第三名维修师傅和第一名管家可以通过审批。
- 第四名维修师傅、第二名管家或第五名任意直属人员均被服务端拒绝。
- 满员时注册申请仍保持待审核；人员离职后对应岗位申请可以通过。
- 直接新增、修改主管、恢复在职和批量导入不能绕过限制。

### 10.2 离职历史

- 离职后原手机号和密码均不能登录，旧 JWT 立即失效。
- `users` 不再存在该账号，`staff_profiles` 保留离职档案。
- 历史工单数量、附件、流转记录和历史绩效在离职前后保持一致。
- 历史页面显示“姓名（已离职）”，当前组织、通讯录、排班和可派单列表不显示该人员。
- 新增同岗位人员后，历史工单不会归到新人名下。

### 10.3 工单权限

- 维修师傅可在报修、投诉、帮助三个页面看到自己的工单。
- 维修师傅可以完整处理自己名下的投诉和帮助工单并提交主管审核。
- 维修师傅无法通过列表、详情、附件、日历或修改接口看到/操作他人工单。
- 同名人员不会造成越权；授权只比较用户 ID。
- 主管可以查看和派发三类工单，并完成最终审核。

### 10.4 自动化验证

- 团队容量服务单元测试覆盖总容量、角色容量、离职释放名额和并发事务边界。
- 账号生命周期测试覆盖真实删除、JWT 失效、历史身份保留和事务回滚。
- 工单接口测试覆盖集合、详情、附件、修改和三类工单状态流转。
- 迁移测试覆盖旧数据回填、同名歧义告警、重复执行和回滚。
- 固定模拟数据验证器确认五个可登录账号、四名在职直属人员、两名离职历史人员及完整工单流程。
- 全量测试通过后才允许合并、推送和生产迁移。
