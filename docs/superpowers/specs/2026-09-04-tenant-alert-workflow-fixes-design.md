# 多企业隔离、工单提醒与现场材料修复设计

## 目标

本次修复覆盖七类线上问题：企业间小区显示串扰、工单导航红点缺失、预警时间不可配置或重启失效、维修人员提交完工后主管未收到提醒、工单流转时间线为空、现场照片无法拍摄或查看，以及退回/搁置后主管未收到再次处理提醒。

## 设计原则

1. 所有业务数据都以服务端认证令牌中的 `tenant_id` 为唯一租户边界，不信任前端传入的企业标识。
2. 浏览器认证信息使用页签级 `sessionStorage`，避免同一浏览器多个企业账号相互覆盖登录状态。
3. 提醒配置和发送进度写入数据库，Render 重启后自动恢复，避免重复或漏发。
4. 工单流转时间线由服务端活动日志生成，不再依赖前端写入的 `metadata.steps`。
5. 现场材料始终通过带 Bearer Token 的请求读取，浏览器不直接访问受保护的图片地址。

## 一、企业与小区隔离

- 小区查询、创建、修改、删除继续由后端根据当前登录账号的 `tenant_id` 限定。
- 同名小区允许存在于不同企业。
- 同一企业内对小区名称执行去首尾空格、忽略大小写的唯一校验，重复创建返回明确错误。
- 对同一企业已有的同名重复小区进行安全归并：保留最早记录，将工单、人员授权、邀请关系等引用迁移到保留记录后再删除重复项。
- 前端的 token、用户、角色和当前小区改为页签级保存；退出时同时清理旧版 `localStorage` 残留。

## 二、工单导航红点

- 报修、投诉、帮助三个入口分别展示当前账号可见且未完结的工单数量。
- 主管看到本企业范围；师傅和管家只看到分配给自己的范围。
- `待派单`、`处理中`、`搁置中`、`待确认`均计入红点，`已完成`不计入。
- 红点在加载工单、派单、接单、提交、退回、搁置、恢复和确认完成后即时刷新。

## 三、自定义预警与持久恢复

- 主管可以设置提醒间隔（分钟），设置保存到租户级配置。
- 新增提醒状态表，记录每张工单在当前状态下最近一次提醒时间。
- 服务启动时扫描所有企业的提醒设置并恢复定时任务。
- 到期后按状态提醒：
  - 待派单：@主管；
  - 处理中：@当前处理人；
  - 搁置中：@主管；
  - 待确认：@主管。
- 工单状态改变时重置该工单的提醒计时，避免沿用旧状态的提醒时间。

## 四、关键流转即时提醒

- 主管派单后：@被派单人员，提示有新的派单。
- 维修人员或管家提交完工后：@主管，提示确认工单。
- 维修人员或管家退回后：@主管，提示重新派单。
- 工单被搁置后：@主管，提示跟进或重新派单。
- 主管确认完成后：发送完结提醒，标明处理人，不进行 @。
- 通知发送失败不回滚工单事务，但记录结构化错误，便于排查外部消息接口。

## 五、完整流转时间线

- 创建工单时记录“工单创建”活动。
- 派单、接单、提交、退回、搁置、恢复、催办、确认完成、驳回均记录操作者、时间和必要说明。
- 工单详情的时间线由服务端活动日志按时间升序生成。
- 对历史工单没有活动日志的情况，使用工单的创建时间、派单时间和完成时间生成兼容节点，保证不再出现空白时间线。

## 六、拍照、上传和预览

- 现场材料提供两个明确入口：“拍照”和“上传照片”。
- “拍照”使用移动设备后置相机；“上传照片”允许从相册或文件选择多张。
- 附件列表和文件内容都通过认证请求获取。
- 图片转换为临时 Blob URL 后显示缩略图，点击可查看大图；非图片附件提供可点击下载入口。
- 关闭工单详情时释放临时 URL，避免浏览器内存持续增长。

## 七、安全和兼容性

- 所有新增查询和写入均带 `tenant_id`，并保持普通员工只能访问本人三类工单的现有规则。
- 不修改已有工单 ID、历史记录和附件文件。
- 提醒任务只在当前 Node 进程中运行，但进度持久化，可在免费 Render 实例重启后恢复。
- 前端升级后旧登录会话可能需要重新登录一次，此后不同页签可安全登录不同企业。

## 验收标准

1. 两个企业可分别创建同名小区，互相不可见；同一企业重复创建会被拒绝。
2. 三类工单入口对所有未完结状态显示正确红点。
3. 自定义提醒保存后，重启服务仍生效，且按状态 @ 正确人员。
4. 提交、退回、搁置分别触发主管提醒，完成提醒不 @ 人。
5. 新旧工单详情均能看到从创建开始的时间线。
6. 手机端可以拍照，桌面和手机均可上传，缩略图可点击查看。
7. 现有租户权限、工单流转和外部接入接口测试继续通过。
