# 外部反馈去重建单与状态超时提醒设计

## 1. 背景与目标

外部 AI 会通过 `POST /api/tickets/external` 提交居民反馈。当前接口收到合法请求后直接进入建单流程，存在以下风险：

- 地址尚未问完整时提前建单和预警；
- 多名居民在短时间内反馈同一地点、同一事件时重复建单；
- 并发请求同时通过“先查后建”判断，产生两张重复工单；
- 合并反馈会覆盖首张工单的反馈人和原文，导致责任来源变化；
- 当前提醒时长为企业统一值，并且“处理中”也会提醒，不符合新的业务口径。

本次目标是把外部接口改为“反馈受理入口”：服务端根据地址完整性、事件和已有工单决定暂存、合并或新建；同时让主管按状态配置超时提醒，“处理中”不提醒。

## 2. 已确认的业务规则

### 2.1 地址不完整

- 外部请求仍返回精确响应 `{"success":true}`。
- 不创建工单。
- 不发送预警群消息。
- 保存一条脱敏的受理决策记录，标记为 `deferred`，便于管理平台追溯为什么没有建单。
- 后续 AI 获取完整地址后应再次调用接口；新请求重新执行去重判断。

地址完整性的判定顺序：

1. 空地址或“未知、待确认、未提供、暂不清楚”等占位地址一律延期，不猜测楼栋、单元或房号；
2. 地址有效且传入 `location_complete` 或 `locationComplete` 时，以显式布尔值为准；
3. 地址有效且未传完整性字段时，默认视为完整。

### 2.2 同一事件的判断范围

在同一企业、同一小区内，同时满足以下条件才视为同一事件：

- 工单未完结；
- 首次创建时间距当前请求不超过 15 分钟；
- 工单类型一致；
- 事件类别或服务端提取的事件特征一致；
- 规范化后的具体位置一致。

位置规范化只处理不会改变语义的差异，例如空格、大小写、全半角和常见连接符。`502` 与 `503` 必须保持为不同位置，不能模糊合并。

### 2.3 三种典型场景

#### 场景一：多人反馈同一地点、同一事件

A 居民先完整反馈“502 着火”，随后 B 居民也完整反馈“502 着火”：

- A 的请求创建一张工单并发送一次预警；
- B 的请求合并到该工单，不重复建单、不重复发送创建预警；
- 工单反馈次数加一，并保留 A 为主反馈人；
- B 的反馈人、原文和请求时间写入来源记录，详情中可追溯。

#### 场景二：多人补充后才形成完整地址

A 先说“着火了”，地址不完整；B、C、D 继续提供信息，最终由 D 的完整请求给出“502”：

- 地址不完整的请求只记录为 `deferred`，均不建单、不预警；
- D 的完整请求创建工单并发送预警，主反馈人是 D；
- 服务端不设置等待或防抖窗口，避免真实紧急事件因聚合而延迟。

该结果依赖上游在信息完整时才提交完整请求。如果 B 已经提交了一个地址完整的 API 请求，服务端必须立即受理，不能等待未来可能出现的 D。

#### 场景三：同类事件但地点不同

A 完整反馈“502 着火”，B 完整反馈“503 着火”：

- 分别创建两张工单；
- 分别发送预警；
- 两张工单独立流转。

### 2.4 已完结工单复发

匹配到 30 天内已完结的同类、同地点工单时，仍按现有复发规则创建新工单、关联历史工单并提升优先级；不会合并到已完结工单。

## 3. 方案比较与选择

### 方案 A：路由内继续“查询后插入”

改动最小，但无法可靠防止两个并发请求同时查不到记录后各自插入，不采用。

### 方案 B：数据库事务串行完成决策、建单和来源记录（采用）

把“校验地址 → 查询重复 → 合并或建单 → 写受理审计”放入同一数据库事务。SQLite 写事务会串行化同一实例内的并发写入，第二个请求在获得写锁后会看到第一个请求创建的工单并执行合并。该方案与当前 SQLite 持久化架构一致，改动范围可控。

消息发送必须在事务提交之后执行，避免外部消息接口卡住数据库写锁；只有本次决策为 `created` 时发送创建预警。

### 方案 C：新增独立消息队列和分布式锁

多实例扩展能力更强，但当前 Render 单实例与 SQLite 架构不需要额外基础设施，成本和复杂度过高，本次不采用。

## 4. 服务端结构

### 4.1 外部受理决策服务

新增独立服务负责以下职责，路由只处理鉴权、租户解析和 HTTP 响应：

- 规范化工单类型、类别和位置；
- 判定位置是否完整；
- 生成稳定的重复事件键；
- 在事务中返回 `deferred`、`merged` 或 `created`；
- 冻结首张工单的主反馈人、反馈群与原文；
- 追加每一次反馈来源；
- 记录脱敏的受理决策。

普通主管在系统内手动创建工单时仍走原有创建逻辑，不应用“地址不完整也返回成功”的外部兼容行为。

### 4.2 受理决策审计

新增租户隔离的受理记录表，保存：

- 企业 ID、小区 ID；
- 可空的工单 ID；
- 决策 `deferred`、`merged` 或 `created`；
- 规范化位置、事件键；
- 反馈人、反馈群、原文；
- 脱敏请求摘要和创建时间。

令牌、机器人 ID、群 ID、联系人映射等敏感或运维字段继续按现有规则脱敏，不写入可查询的请求摘要。

## 5. 并发与一致性

- 外部受理使用立即写事务，重复检查与插入之间不释放写锁。
- 工单编号生成也必须位于同一事务中，避免并发生成相同 `WX` 编号。
- 合并只增加 `feedback_count`、更新重复键并追加来源记录，不覆盖主反馈人、主反馈群和主原文。
- 数据库提交成功后再调用预警接口；预警失败不回滚工单，但保存安全失败状态供日志与后续人工重试。
- 所有查询必须包含服务端确定的 `tenant_id` 和 `community_id`，客户端不能直接指定租户 ID。

## 6. 外部 API 兼容约定

### 6.1 请求字段

继续兼容现有字段，并新增可选字段：

- `location_complete` / `locationComplete`：可选布尔值；
- `feedback_person` / `feedbackPerson` / `sender_name` / `senderName`：反馈人；
- `message`：原文消息的标准字段；仅当 `message` 为空时，才兼容使用旧字段 `original_message` / `originalMessage`。
- 反馈人字段均为空时，工单和预警不虚构反馈人，也不显示“反馈人”一行。

### 6.2 响应

所有已通过鉴权与基础格式校验的受理结果统一返回：

```json
{"success":true}
```

该响应仅表示“反馈已被系统受理”，不等同于“一定创建了新工单”。未知企业、非法令牌、非法工单类型、未知小区等仍返回现有稳定错误码。

## 7. 状态超时提醒

### 7.1 主管设置

管理工作台“设置”中的“工单未处理提醒”调整为按状态配置：

- 待派单 `wait`：可配置分钟数，超时后 @主管；
- 搁置 `pending`：可配置分钟数，超时后 @主管；
- 待确认 `confirm`：可配置分钟数，超时后 @主管；
- 处理中 `doing`：固定关闭，不提供提醒时长输入，也不进入定时扫描；
- 已完成 `done`：不提醒。

每项允许填写 1—1440 分钟，填 0 表示关闭该状态提醒。配置按企业隔离并持久保存。

### 7.2 退回与驳回

- 处理人退回后工单回到 `wait`，立即 @主管重新派单，并从退回时间重新开始“待派单”计时；
- 主管驳回完成申请并转单后，按转入的实际状态重新计时；
- 若驳回后回到待派单，则立即 @主管，并应用 `wait` 的超时设置；
- 状态变化时清除上一状态的提醒发送记录，禁止沿用旧状态计时。

### 7.3 重复提醒

工单在某状态达到配置时长后发送第一次提醒；若状态未变化，此后每隔同样时长再次提醒。状态改变、工单完成或对应状态设置为 0 后停止提醒。

## 8. 错误处理

- 无效的 `location_complete` 返回稳定的 `INVALID_LOCATION_COMPLETE`；
- 提醒分钟数不是整数或超出 0—1440，整次保存失败并返回稳定校验错误；
- 事务失败时不产生部分工单、部分来源或部分决策记录；
- 预警接口失败只返回安全错误码到服务端日志，不输出令牌、群 ID、机器人 ID 或联系人 ID；
- 服务重启后从持久化配置和提醒状态恢复调度，不重复发送尚未到期的提醒。

## 9. 测试与验收

### 9.1 外部受理测试

- 地址不完整：返回 `success`，工单数不变，预警次数为零，存在 `deferred` 决策记录；
- A/B 同地点同事件：一张工单、一次创建预警、反馈次数为二、主反馈人为 A、两条来源可查；
- A/B/C 地址不完整、D 完整：一张工单、主反馈人为 D、只发送一次预警；
- 502 与 503：两张工单、两次预警；
- 并发提交相同反馈：最终仅一张工单，另一请求合并；
- 已完结后复发：创建新工单并保留历史关联；
- 跨企业同小区同位置：互不合并。

### 9.2 提醒测试

- `wait`、`pending`、`confirm` 分别按自己的分钟数触发并 @主管；
- `doing` 无论停留多久都不发送超时提醒；
- 状态变化后旧状态提醒不再触发，新状态从变更时间重新计时；
- 未改变状态时按间隔重复提醒；
- 配置、提醒状态和消息目标严格按企业隔离；
- 服务重启后恢复定时任务且不提前或重复发送。

### 9.3 回归范围

- 外部创建成功响应保持为 `{"success":true}`；
- 派单、提交待确认、退回、搁置和完工即时消息保持现有行为；
- 工单列表、详情、时间线、来源查询与绩效统计不因合并逻辑产生回归；
- 完整测试集必须通过。

## 10. 不在本次范围

- 不在服务端等待多轮对话结束，也不为紧急事件增加防抖延迟；
- 不通过相似度模型猜测两个不同地址是否相同；
- 不引入 Redis、外部队列或新的付费服务；
- 不改变已完结工单的复发规则；
- 不改变预警群、机器人和联系人配置方式。
